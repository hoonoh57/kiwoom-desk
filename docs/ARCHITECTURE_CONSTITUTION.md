# Kiwoom Desk Architecture Constitution

## 1. 프로젝트 정체성

Kiwoom Desk는 키움증권 REST API와 WebSocket API를 표준 방식으로 구현하고,
실제 사용 가능한 MDI형 HTS 워크벤치로 완성하는 기준 프로젝트다.

이 저장소의 최우선 목표는 다음과 같다.

1. 키움 REST/WebSocket 계약의 정확한 구현
2. 각 API 기능의 독립적인 개발과 검증
3. 실제 사용 가능한 MDI형 HTS 화면 구성
4. 폼 간 표준 종목 연동
5. 오류 복구와 재현 가능한 검증
6. 완성된 표준 기능의 안정적인 보존

## 2. 표준 프로젝트의 포함 범위

다음 기능은 Kiwoom Desk에 포함한다.

- 키움 REST API별 표준 조회 화면
- WebSocket LOGIN, 재접속, 요청 직렬화
- 조건검색 목록, 일반검색, 실시간 등록과 해제
- 종목정보, 차트, 계좌, 잔고, 주문, 미체결
- 실시간 현재가, 체결, 체결강도, 호가
- 주문 접수, 체결, 미체결 진행 대시보드
- Dock, 탭, 분할, 부동창, 크기 조절
- 사용자 화면 배치 저장과 복원
- 선택 종목의 차트, 주문, 호가, 체결 화면 동기화
- API 원본값의 표시상 정규화
- 표준 열 정렬, 숨김, 검색, 내보내기
- 연결 상태, 오류, 원본 응답 확인 기능

## 3. 표준 프로젝트의 제외 범위

다음 기능은 별도 응용 프로젝트에서 구현한다.

- 후보 종목 상대강도 순위
- 누적 거래대금 또는 거래대금 속도 점수
- 여러 피처의 합성점수
- Top N 매매대상 자동선별
- 전략별 진입과 청산 판단
- 자동매매 실행 정책
- 전략 성과평가와 최적화
- MFE, MAE, 승률, 기대수익 분석
- 머신러닝과 딥러닝 매매 판단

## 4. 표준 기능과 응용 기능의 경계

API가 제공한 값 또는 그 값의 표시상 정규화는 표준 기능이다.

여러 값을 결합해 매매 우선순위, 점수, 신호 또는 전략적 판단을 만드는 것은
응용 기능이다.

예:

- 현재가 표시: 표준
- 누적거래대금 표시: 표준
- 등락률 표시: 표준
- 원본 열 내림차순 정렬: 표준
- 조건검색 종목을 선택해 차트와 주문 화면에 전달: 표준
- 후보군 내부 거래대금 percentile: 응용
- 상대강도와 거래대금의 합성점수: 응용
- 점수 상위 5종목 자동매수: 응용

## 5. MDI HTS 원칙

Kiwoom Desk는 단일 화면이나 API 예제 모음이 아니다.

사용자는 다음 화면들을 필요에 따라 동시에 열고 자유롭게 배치할 수 있어야 한다.

- 조건검색 결과 그리드
- 실시간 편입과 이탈
- 틱, 분, 일, 주, 월, 년 차트
- 실시간 체결
- 체결강도
- 호가창
- 주문
- 미체결
- 계좌와 잔고
- 주문과 체결 진행 대시보드
- 로그와 원본 응답

각 화면은 다음 기능을 지원해야 한다.

- 독립적인 열기와 닫기
- 탭 결합
- 수평과 수직 분할
- 크기 조절
- 부동 패널
- 위치 이동
- 레이아웃 저장과 복원

## 6. 폼 연동 원칙

폼끼리 직접 참조하지 않는다.

폼 간 연동은 EventBus 또는 공개 서비스 계약을 사용한다.

종목 선택의 표준 이벤트는 `Topics.SymbolSelected`다.

조건검색, 관심종목, 종목조회 등에서 종목을 선택하면 다음 화면들이
동일한 종목을 반영할 수 있어야 한다.

- 차트
- 주문
- 호가
- 체결
- 체결강도
- 종목정보

이미 열려 있는 폼은 선택 종목을 즉시 반영한다.

닫혀 있는 폼은 사용자의 명시적인 열기 명령으로 생성한다.

동일 폼의 중복 생성 정책은 `InstancePolicy`가 결정한다.

## 7. 인스턴스 정책

- `singleton`: 앱 전체에서 하나만 존재한다.
- `per-api`: API 또는 표준 키별로 하나씩 존재한다.
- `multi`: 요청할 때마다 새 인스턴스를 생성한다.

호출 측에서 임의로 패널 키를 만들지 않는다.

패널 키와 중복 정책은 DockService와 폼 registry에서 중앙 관리한다.

## 8. API 폼 구현 원칙

각 API 폼은 다음을 명확히 구분한다.

1. 요청 입력
2. API 호출
3. 원본 응답
4. 응답 정규화
5. 화면 표시
6. 사용자 종목 선택
7. 오류와 빈 데이터 상태
8. 연속조회 상태

API 폼 안에 특정 매매전략이나 후보 점수 계산을 넣지 않는다.

원본 응답을 전략 편의에 맞게 변형하지 않는다.

## 9. WebSocket 구현 원칙

- LOGIN 완료 전 요청을 전송하지 않는다.
- 같은 응답 종류의 요청은 응답 매칭이 보장되도록 직렬화한다.
- 요청 응답과 실시간 데이터 패킷을 구분한다.
- timeout 이후 늦은 응답이 다른 요청에 연결되지 않도록 한다.
- 연결 단절 시 요청 상태를 정리한다.
- 재연결 후 서버 등록 상태와 로컬 상태를 다시 동기화한다.
- 실시간 등록과 해제는 실제 성공 응답 후 상태를 확정한다.

## 10. Stable 단계

기능 상태는 다음 단계로 관리한다.

`Planned -> Implemented -> Tested -> Stable`

Stable 전환 조건은 다음과 같다.

1. API ID와 요청 필드 확인
2. 응답 필드 확인
3. 정규화 규칙 확인
4. 모의투자 실제 호출 검증
5. 성공 응답 검증
6. 실패 응답 검증
7. 빈 응답 검증
8. 연속조회 또는 실시간 수명주기 검증
9. 재접속과 timeout 검증
10. TypeScript 검사 통과
11. production build 통과
12. 공백과 개행 검사 통과
13. 다른 표준 폼과의 연동 검증
14. 재현 절차 또는 fixture 확보
15. 완료 커밋 기록

## 11. Stable 기능 변경 규칙

Stable 기능은 다음 사유에 한해서만 변경한다.

- 확인된 버그
- 키움 API 계약 변경
- 오류 복구 문제
- 성능 문제
- 보안 문제
- 테스트로 증명된 호환성 개선

특정 전략이나 응용 화면의 편의를 위해 Stable API 계약이나 기본 폼 동작을
변경하지 않는다.

## 12. 응용 프로젝트 원칙

응용 프로젝트는 Kiwoom Desk의 검증된 공개 계약을 사용한다.

응용 프로젝트에서 구현할 수 있는 기능은 다음과 같다.

- 조건검색 후보군 저장소
- 실시간 피처 계산
- 상대강도와 거래대금 점수
- Top N 선별
- 전략 실행
- 자동매매
- 성과 검증
- 시뮬레이션과 재생
- 데이터베이스 저장
- 머신러닝 추론

응용 프로젝트는 표준 폼의 private 상태에 접근하지 않는다.

응용 로직은 표준 API 클라이언트와 원본 폼을 변경하지 않는다.
